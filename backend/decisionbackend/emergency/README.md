# Emergency Decision Backend

This module implements the **Emergency Vehicle Decision Subsystem** for the 4-approach traffic signal decision engine.

---

## Architecture & Roadmap

```
Hospital / Emergency Dispatch
        │
        ▼
EmergencyMissionContext / EmergencyOrchestrator (Phase 5)
        │
        ├──► Camera / VideoProcessor / Frame Ingestion Loop
        │           │
        │           ▼
        │    VehicleTracker (ByteTrack)
        │           │
        │           ▼
        │    TrackedVehicle (persistent local track_id, speed_px, center)
        │           │
        │           ▼ [Phase 4B Bridge]
        │    EmergencyVisionBridge
        │           │
        │           ▼ [Phase 4A Event Contracts]
        │    EmergencyDetectionEvent, EmergencyEtaUpdateEvent,
        │    EmergencyPassageEvent, DirectionalHandoffEvent
        │           │
        │           ▼
        └──► CameraIntegrationAdapter (Phase 4A Adapter)
                    │
                    ▼ [Domain Commands]
             EmergencyController (Phase 1, 2, 3 Decision State Machine)
                    │
                    ▼
             SignalController (Phase Decisions & Clearance Transitions)
```

* **Phase 1 (Foundation)**: Emergency data models, live ETA countdown, dynamic clearance ($T_{clear}$), dynamic effective $G_{max}$, and passage event interfaces.
* **Phase 2 (Single Emergency Engine)**: Single emergency state machine, $G_{min}$ protection, Case A & B urgency trigger evaluations, clearance transitions, emergency green servicing & extensions, passage confirmation, dynamic dismissal, and wait-time recovery.
* **Phase 3 (Multi-Emergency Management & Clustering)**: Multi-emergency queue ordering, dynamic transitive ETA clustering ($\le 10\text{s}$), temporary $2\times$ queue priority boosting ($0.45 \to 0.90$), independent cluster trigger evaluations, 4-tier conflict resolution, and dynamic re-clustering on passage/dismissal.
* **Phase 4A (Camera & Tracking Event Layer)**: Strongly typed camera/tracking event contracts (`EmergencyDetectionEvent`, `EmergencyEtaUpdateEvent`, `EmergencyPassageEvent`, `DirectionalHandoffEvent`), decoupled `CameraIntegrationAdapter`, input validation, downstream automated handoffs, and test suite.
* **Phase 4B (Vision-to-Emergency Bridge)**: Direct bridge (`EmergencyVisionBridge`) connecting `VehicleTracker` / `TrackedVehicle` telemetry to `CameraIntegrationAdapter`, live distance/speed ETA calculation, virtual line-crossing passage detection, and `CORRIDOR_MAP` directional handoffs.
* **Phase 5 (End-to-End Multi-Junction Orchestration)**: Multi-junction coordinator (`EmergencyOrchestrator`), `EmergencyMissionContext` lifecycle, camera-local `track_id` recycling, seamless J1 $\to$ J2 corridor handoffs, independent downstream ETA generation, and simultaneous multi-corridor emergency handling.

---

## PHASE 5 — MULTI-JUNCTION ORCHESTRATION

### 1. Persistent Identity vs. Camera-Local Tracking
* `emergency_id` represents the persistent vehicle/mission identity across the entire journey.
* `track_id` is camera-local and generated by ByteTrack. When passing a junction and arriving at the downstream camera, `EmergencyOrchestrator` allows a fresh `track_id` to be bound without stale track ID leakage.

### 2. Multi-Junction Corridor Progression
* Each junction operates an independent `EmergencyController` instance.
* Passage at an upstream junction (e.g. J-04) transitions only that junction into clearance/recovery while updating `EmergencyMissionContext` status to `TRANSIT_TO_HOSPITAL`.
* Downstream junction (e.g. J-01) receives an independent ETA and independently schedules its emergency green sequence.
* When the vehicle completes all corridor nodes, the orchestrator updates status to `MISSION_ACCOMPLISHED`.
